# lib/multimod

Cyclic convolution modulo an NTT prime chosen at run time, for products modulo several primes
joined by the CRT. API and usage: the header of `transform.hpp`. Tests: `test.cpp`. Timing:
`bench.cpp`. Kernels: `kernels.hpp`, generated by `gen_kernels.py` (do not edit).

## Design

- lib/ntt's transform (recursion, tables, kernels; `lib/ntt/notes.md`) with p a variable.
  `gen_kernels.py` runs lib/ntt's generator and rewrites 6 lines: P, 2P and -1/P mod 2^32 become
  globals that `Modulus::select()` sets before each prime. The instructions are the same.
- Lengths 2^6..2^20; a prime needs p < 2^30 and 2^17 | p - 1. Twiddle tables are rebuilt per
  prime (2^lg / 16 entries each way, AVX2).
- First level (sparse: count <= 2^lg / 2):
  - lg even >= 8, both inputs sparse: one radix-8 pass reads the input, reduces it and writes
    the first radix-4 group of both halves.
  - lg odd: radix 4. A sparse input is reduced and transformed in one pass.
  - Otherwise: reduce into the array, then a radix-2 level (a copy when sparse).
  The scale (and the caller's factor) is fused into the last inverse level.
- Inputs: `Padded` (words < 2p, zero up to half the length: plain loads), `Bounded` (words
  < 2p, masked loads at the end, nothing read past the count), `Wide` (64-bit words,
  hi (2^32 mod p) + lo, for p > 2^29). `detail::Narrow<Input>` turns 8 words into canonical
  residues.
- `multiply` takes the inputs by value, and the first-level passes build `Narrow` from the input
  and the `Modulus` inside the function. `Vec` is `may_alias`, so state behind a reference is
  reloaded after every vector store; by value it stays in registers and shares p and 2p with
  the pass.

## Users

| Problem | Input | Primes |
|---|---|---|
| convolution_mod_1000000007 | Padded | 3 |
| convolution_mod_2_64 | Wide | 5 |
| multivariate_convolution_cyclic | Bounded | 3 |

Not moved: `multivariate_convolution/transform.hpp` is a different transform (P = 998244353,
forward and inverse as separate steps), not a copy.

## Log

2026-10-10, claude (issue #156, round 1). `lc-amd` (EPYC 7B13), GCC 15.2 in the pinned image,
judge flags.
- Extracted from the three problems' copies (cyclic's was the newest). Their `kernels.hpp` were
  identical apart from line 1; the 1e9+7 and 2^64 transforms differed only in input
  narrowing, which is now the `Input` parameter.
- Behaviour change for 1e9+7 and 2^64: at odd lg (2^7..2^19) a sparse input is reduced and
  transformed in one pass (cyclic's code), not reduced into the array first. The lg 20 path
  (their slowest tests) is the same logic.
- First version (inputs by `const&`): `Transform::multiply` grew in all three
  (cyclic 3855 -> 4185 bytes): the inputs were reloaded after each aliasing store. By value:
  cyclic's transform functions became instruction-identical to main's; only `solve()` kept a
  different register allocation (same calls, 3457 vs 3466 instructions).
- `Narrow` by `const&` (as in the old copies) reloads its constants and pointer in every
  radix-8 iteration; built inside the pass, they stay in registers. `Transform::multiply` alone
  (a `bench.cpp`-like harness, one binary per kind and variant, the old call for the old
  copies; two sessions of 15 interleaved rounds, each a median of 21 runs; median of the
  paired ratios to the problem's old copy):

  | lg 20, n = m = 2^19 | old ms | inputs by value | + `Narrow` by value | + built in the pass (kept) |
  |---|---|---|---|---|
  | Padded, 3 primes | 13.70 | 1.0041 | 0.9979, 0.9999 | 1.0009 |
  | Wide, 5 primes | 23.82, 23.88 | 1.0060 | 1.0028, 1.0004 | 1.0005 |
  | Bounded, 3 primes | 13.90 | 0.9995 | 0.9942, 0.9925 | 0.9945 |

  Two values: first and second session (the kept variant ran in the second only). The middle
  variant's sessions differ by up to 0.25%: that is the noise. Kept for the simplest code.
  At lg 19, n = m = 2^18 (11 rounds), the fused first level gains: Padded 0.9837 (old
  6.648 ms), Wide 0.9904 (11.485 ms), Bounded 0.9991 (6.582 ms; cyclic had it already).
- Whole programs, `judge.py bench`, 31 rounds, against main's `main.cpp`: 1e9+7 0.9991
  (24.50 -> 24.78 ms median), 2^64 0.9998 (44.70 -> 44.74), cyclic 0.9944 (11.37 -> 11.32).
- Checks (`lc-intel`): `test.cpp` passes at -O2 (x86-64-v3 and native) and with ASan/UBSan;
  official tests 48/48, 44/44, 24/24. A test variant with Wide's work in b's storage fails
  (b's 64-bit words are overwritten before they are read), so the header allows only a's.
- An untimed run had shown cyclic's twos_02 at 102.7 ms on `lc-intel`. Not reproduced: three
  locked runs each of main and this branch gave 1.9-2.1 ms.
